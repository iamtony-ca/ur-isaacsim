# cuMotion robot config (UR16e + 2F-85)

GPU motion planning for the UR16e via **NVIDIA Isaac ROS cuMotion** as a MoveIt
planning pipeline. cuMotion plans on the GPU; execution stays on our existing
`scaled_joint_trajectory_controller` (sim or real).

## Files
- `ur16e_2f85.xrdf` — cuMotion robot config (cspace, collision spheres, self-collision)
  for UR16e + GRP-ES-CPL-077 coupling + 2F-85. Generated by `gen_xrdf.py`. Two sphere
  sets (2026-10-16, `../../HISTORY.md` §51):
  - **world** (`collision`: obstacles, nvblox ESDF, robot_segmenter) — spheres that
    **cover** the collision mesh of every link except the base housing (which sits on the
    table and has no world spheres): ≤ 20 mm overshoot on the arm/coupling, ≤ 10 mm on the
    gripper, 195 spheres. Mesh inside spheres + 5 mm buffer on all 16 links;
  - **self** (`self_collision`) — covering spheres only on the links that touch each other
    (forearm, wrist_2, wrist_3, coupling at 5 mm; base housing at 20 mm), inner spheres
    elsewhere, 453 spheres.
- `ur16e_2f85.urdf` — flattened UR16e+2F-85 URDF with **absolute `file://` mesh paths**
  + `gripper_frame`/`grasp_frame` (cuMotion tool/grasp frames). What the cuMotion
  node loads. (Mesh paths point at `/opt/ros/jazzy/share/...`; regenerate if your
  install prefix differs.) It predates the current apt `ur_description`: the wrist_3
  visual/collision origin differs from today's xacro by 0.5 mm — not regenerated yet.
- `gen_xrdf.py` — regenerates the XRDF from the URDF meshes + the shipped ur10e template.
  It always writes the shipped `ur16e_2f85.xrdf` (copy the script elsewhere for an A/B candidate).
- `check_xrdf.py` — mesh coverage per link (pass ≤ 5 mm), named poses free of
  self-collision and above cuMotion's ground plane.

## Why two sphere sets (measured 2026-10-16)
The first XRDF (template spheres + 12/10/4 medial spheres for upper arm/forearm/coupling)
sat **inside** the meshes: the meshes stuck out of spheres + 5 mm buffer by up to 39 mm
(forearm), 34–35 (upper arm, depending on the surface sampling), 32 (coupling), 28 (shoulder),
23 (knuckles) — all measured against spheres + the 5 mm buffer. cuMotion could
call a path free with an obstacle that deep in the arm. The template's self-collision
ignore list also skipped forearm ↔ wrist_2/wrist_3, which MoveIt checks and which do
collide; the base housing had no spheres at all.

| | old XRDF | **current** |
|---|---|---|
| world: mesh outside spheres + buffer, worst link | 39 mm | ≤ −2 mm (`check_xrdf.py`; base housing has no world spheres) |
| self vs MoveIt, 1000 random configs (210 in collision) | 49 missed / 3 false alarms | **5 / 48** |
| cuMotion plan only, empty scene, 25 joint goals from `ready` (median planning time) | 24/25, 0.078 s | 24/25, 0.182 s |

Covering spheres on every link at 20/30 mm overshoot refuse 52/92 % of the 790
collision-free configs (mostly base housing ↔ upper arm, then forearm ↔ wrist_2); at 5 mm
everywhere they are accurate (0 missed / 51 false alarms) but need 1315 spheres — hence the
mix. The 48 false alarms are mostly forearm ↔ wrist_2 (30) and forearm ↔ coupling (15)
near-contacts (mesh distance not measured). The cuMotion pipeline has no `ValidateSolution`
response adapter, and with `ur_only:=true` MoveIt has no gripper, so nothing re-checks a
cuMotion plan against the meshes before execution (MoveIt only re-validates the remaining
path when the planning scene changes during execution). Whether the UR controller itself
protects against self-collision was not checked here. So missed self-collisions were weighted
above false alarms.

## Regeneration
```bash
cd /isaac-sim/volume/ur_ws
# 1) (only if the robot model changed) flatten the URDF: xacro, package:// -> file://
source /opt/ros/jazzy/setup.bash && source install/setup.bash
xacro src/ur_bringup/urdf/ur16e_2f85/ur16e_2f85_sim.urdf.xacro \
  | sed 's#package://#file:///opt/ros/jazzy/share/#g' > /tmp/ur16e_2f85.urdf
#    then append ONLY grasp_frame + grasp_joint (parent gripper_frame, xyz 0 0 0.20) as in the
#    shipped file -- gripper_frame now comes from the xacro (urdf/common/robotiq_2f85_macro.xacro)
cp /tmp/ur16e_2f85.urdf src/ur_bringup/cumotion/ur16e_2f85.urdf   # the scripts below read THIS path
# 2) spheres: Isaac Sim 6.1 ships the `cumotion` python module + trimesh (checked on 6.1.0-rc.26 only)
/isaac-sim/python.sh src/ur_bringup/cumotion/gen_xrdf.py      # -> ur16e_2f85.xrdf (deterministic)
/isaac-sim/python.sh src/ur_bringup/cumotion/check_xrdf.py    # must print PASS
```
(Outside Isaac Sim: a venv with NVIDIA's standalone `cumotion` wheel + trimesh + pyyaml —
untested with this script.)
A/B another XRDF without replacing the shipped one (the PLANNER only — the nvblox launch's
robot_segmenter always loads the shipped file; leave the argument out rather than passing it empty):
`ros2 launch ur_bringup ur16e_2f85_d405_cumotion_moveit.launch.py xrdf:=/abs/path.xrdf`.

## Run (sim)
```bash
ros2 launch ur_bringup ur16e_2f85.launch.py                              # control (or _d405 / real)
ros2 launch ur_bringup ur16e_2f85_d405_cumotion_moveit.launch.py        # move_group + cuMotion (RViz)
python3 src/ur_bringup/isaac/common/moveit_plan_execute_demo.py          # programmatic plan+execute
```
- **`ur_only` (default true)** — move_group/RViz use a UR-arm-only (6-joint) model +
  plain ur SRDF so **interactive RViz** cuMotion works (the plugin doesn't filter the
  request's full start_state; RViz sends the whole robot state, so a 12-joint start is
  rejected against the 6-joint c-space). cuMotion still plans WITH the gripper
  (collision spheres come from this XRDF). `ur_only:=false` keeps the full
  gripper-aware move_group but then only **programmatic** cuMotion works (empty
  start_state, e.g. the demo); interactive RViz `<random valid>` will fail.
- In RViz: planner = `isaac_ros_cumotion` (default; Context tab) -> Goal State /
  marker -> **Plan -> Execute**.
- **Planner never comes up** (seen several times on 2026-10-16; the failing logs were not
  kept): the container logs `failed to send response to /cumotion_container/_container/load_node
  (timeout)` right after the static planning scene server, `cumotion_planner` never logs, and
  move_group later says `Action server not available after waiting`. Probably a DDS discovery
  race in the component loading, not the config — relaunch. Once a running planner also
  stopped answering mid-benchmark. Either way the `ros2 launch` parent needed SIGTERM.
- **Reset / recover pose**: repeated planning can drift a wrist past +/-2*pi -> MoveIt
  then rejects all plans ("start state out of bounds"). Recover with:
  `python3 src/ur_bringup/isaac/common/reset_pose.py home`  (direct-to-controller,
  works even out of bounds; also `up` / `zero`). RViz named states (home/up) work
  too once in bounds.

## Real-time obstacle avoidance (world collision) — DONE (sim)
> Validated with the pre-2026-10-16 XRDF. **Not yet re-run with the regenerated spheres**
> (only the robot_segmenter's start-up with the new file was checked, `../../HISTORY.md` §51.3).
cuMotion only does self/scene collision until you feed it a world ESDF. This is
now wired with **isaac_ros_nvblox** + **robot_segmenter**:

    ros2 launch ur_bringup ur16e_2f85_d405_nvblox.launch.py            # segmenter + nvblox + static-cam TF
    ros2 launch ur_bringup ur16e_2f85_d405_cumotion_moveit.launch.py read_esdf_world:=true

Pipeline: `static workspace camera depth -> robot_segmenter (mask robot) -> nvblox
(3D ESDF, base_link) -> cuMotion` (cuMotion reads `/nvblox_node/get_esdf_and_gradient`).

**Key lesson:** map with a STATIC workspace camera, NOT the eye-in-hand D405 — the
wrist camera mostly sees the robot and moves with it, polluting the TSDF so the
start pose is reported in world collision. The D405 stays grasp/vision-only.
Config `config/ur16e_2f85_d405/nvblox_cumotion.yaml` (nvblox `global_frame` MUST
equal cuMotion's XRDF base frame = `base_link`). Full write-up + gotchas:
`../../HARDWARE.md` §4, `../../HISTORY.md` §12.

See `../../HARDWARE.md` §4 for the Isaac ROS cuMotion install (apt repos, CUDA 13,
VPI) and the ABI/JTC gotchas.
